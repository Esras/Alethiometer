## User decisions (don't re-ask)

- **Agents (2026-10-03):** build the whole tab. Local ACP live; Scion built as best as possible from the latest source (the user runs a Hub that this environment can't reach; it already has known bugs), gaps left documented for an agent with Hub access. Harnesses use their own login (no provider forced; not Bedrock). Agents must keep running through app quits and **dev rebuilds** (the user runs the in-progress app, whose rebuilds restart it), including ones waiting on an approval: hence the agent host daemon (2026-10-03), a separate rarely-changing crate in this repo, started on demand (no login item), Unix socket, no network port. A2A was considered and rejected for this (no tool-call/approval detail; Claude/Pi don't speak it). **No Alethiometer allowlist:** "Always" is the agent's own option and the agent stores the rule; Explained never suggests what to trust. Edits inside the project shouldn't gate (agent's accept-edits mode); shell commands, scripts and arbitrary node/bash are what matter. Use a battle-tested parser (tree-sitter-bash), not a hand-rolled one. Agents in Incoming followed once its design (2a–2c) landed. Explained, facts box, Unsorted guess and Settings › Agents are in.

Keys picked to fit the app: ⌥↵ Glean, ⌘T link to topic, ⌘⌫ reject, ⌘↵ stays the Search view.

- **Pickers, reclassify, merge (2026-10-01):** pickers open in one fixed spot per view (bottom of the panel, floating, nothing shifts); reclassify from the chronology and from a Search view; a reclassified signal is filed straight away; merging A into B: from the Topics index or topic detail with `m`, A is deleted, A's note is appended into B's, Gmail threads are relabelled to B's category, and the merge is only written when you leave the screen (`u` cancels before then; no confirm step).

Only triage in Alethiometer (confirm, move or dismiss) closes a signal. The other direction stays: confirming here marks top-level items read in Slack, and marking mentions read up to the mention is fine. **A thread (parent + replies) is one topic**; new replies, the user's own too, come back to Incoming under it. **A thread attaches to its parent message**: its replies are stored under the parent in whichever item holds it (the top-level run, triaged or not, or the split part it went to), move with it in splits, and new replies bring that item back. Only threads whose parent was never captured (older than the lookback, unfollowed channel) get their own thread item, with the parent and every earlier reply as context. Thread items from before this rule keep being updated as they were. **DMs and channels mix topics**, so top-level messages are classified per message (grouped by topic, the reason for the split review 15g/15h); the AI sees earlier messages with their topics as context. Slack will be noisy; the user accepts that. First live sync with `lookback_hours: 12`. Websocket first, polling as catch-up. Missing messages is the main concern. A safety catch-up runs every 3 hours while connected.

The split review (15g/15h) corrects an AI split in Incoming; `s` on a confirmed signal in the chronology or search (18c/18d) opens the same review; and (user, 2026-10-01) `s` also opens it on any unsplit Slack signal in Incoming with more than one message, under a topic too. Confirm stays one key.

Person notes in `People/` hold coworker details and stay in this vault.
- Google sign-in: fine with re-auth every 7 days if needed; one Connect button saves the token.
- **AI-proposed topics should be 2 to 5 words and fairly broad** (a recurring subject, not a one-off event's title).
- **Dismissing a signal in Incoming without linking it to a topic**: built (design 13a, `d`/`u`).
- Calendar: quiet first sync (only pending invites surface); one Incoming row per recurring series, but the topic timeline shows individual instances (past + next upcoming only). Horizon trickle of new instances is fine.
- GCP: no personal projects (user blocks project creation org-wide); reuse existing Internal tooling project.
- Jira: assigned/reported/watched issues are usually already filed — their updates should still be *seen* in Incoming, not re-triaged. New issues in DEVOPS/IT/ITP2 (projects the user owns, small volume) should surface. Missing creations while the app is closed >7 days is fine.
- Updates to filed things must show in Incoming. Slack: before triage, new messages join the open signal; after triage, a thread's next replies come back on the same item under its topic, and a top-level run starts a new item the AI classifies per message.
- Background AI suggestions should appear promptly, and new topics shouldn't jump to the top of the list.
- Name: Alethiometer.
- **Reading anything in its own app never removes it from Incoming. This applies to every source.** Gmail's exception is *leaving the Inbox*: if the user archives or trashes a thread in Gmail, it wasn't worth filing, so it leaves Incoming. Reading in Gmail changes nothing.
- Gmail: the Inbox is what's in Incoming, all of it, read or not. Mail filtered out of the Inbox or deleted never needs to reach Alethiometer. Threads move together (never split across topics). Filing to a topic labels the thread with its category's label (`category_labels`, nested labels as `Parent/Child`), marks it read and **archives it, with or without a todo** (user, 2026-10-01; supersedes "follow-ups stay in the Inbox until done"). Never archived past unread mail that arrived after you looked. Dismiss archives (not delete); trash is its own action (`#`).
- **Incoming is where everything gets viewed.** No message is marked seen automatically. An update on a filed item stays in Incoming until the user acts on it here (Confirm, Move or Dismiss; updates use Confirm too, never "Seen").
