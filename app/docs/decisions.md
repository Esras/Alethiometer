- Slack: **Incoming is for assigning context to topics, not "have I read this".** Every message is captured, the user's own included (switching to Slack to reply must not lose the thread's context); Slack's read marker plays no part. The other direction stays: confirming here marks top-level items read in Slack, and marking mentions read up to the mention is fine. **A thread (parent + replies) is one topic**; new replies, the user's own too, come back to Incoming under it. **A thread attaches to its parent message** while the item holding the parent is in Incoming: its replies are stored under the parent in that item (the top-level run or the split part it went to) and move with it in splits. Once that item is triaged, the thread's next replies are their own thread signal, with only the parent and earlier replies as context, under the item's confirmed topics (user, 2026-10-21: two threads updated in one channel are two signals; a thread signal carries no channel context). Threads whose parent was never captured (older than the lookback, unfollowed channel) get their own thread item from the start. Thread items from before this rule keep being updated as they were. **DMs and channels mix topics**, so top-level messages are classified per message (grouped by topic, the reason for the split review 15g/15h); the AI sees earlier messages with their topics as context. Slack will be noisy; the user accepts that. First live sync with `lookback_hours: 12`. Websocket first, polling as catch-up. Missing messages is the main concern. A safety catch-up runs every 3 hours while connected.
