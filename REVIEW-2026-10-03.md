# Architecture and correctness review — 2026-10-03

Seven parallel reviewers plus a lead pass over `app/` (Rust core, agent host, Svelte UI), all read-only.

- **Baseline:** `cargo test --no-default-features` passes (396 unit + 5 integration tests). `svelte-check` is clean.
- **Scale numbers:** measured on a scratch DB built from the real migrations, holding 200k items, 800k messages, 140k topic links, 300 topics and 40k events.
- **"Verified":** the lead re-read the code path. Every other entry was traced by its reviewer.

Priorities applied: accuracy > performance, maintainability > speed of development.

## P0: freezes, data loss, security (fix first)

| # | Where | What happens | Verified |

| 1 | `agents/acp.rs:639→825→1726→1797→1697` | **App-wide deadlock.** `on_event` holds `store.gate()` (a std, non-reentrant mutex) and calls `finish_prompt`. When a message is queued, `finish_prompt` calls `prompt()`, which takes `gate()` again on the same thread. Next, the flush thread takes `app.db()` and then blocks on the gate, so the only DB connection is held forever and the whole app freezes. ## P1: correctness

**Sync and connectors**
- **Items that leave a query are never refreshed.**
  - Jira: the "created in DEVOPS/IT/ITP2 in the last 7 days" clause.
  - GitHub: PRs reached only through `review-requested:@me`.
  - Effect: resolved, merged or reassigned items (and their todos) stay open forever (`jira.rs:122`, `github.rs:262-271`). Needs a periodic "refresh known open items" pass.
- **GitHub misses or drops data.**
  - It replaces stored messages with only the newest batch of comments, so earlier unseen comments disappear (`github.rs:419-440`).
  - `updated:>=cursor` has no overlap window, against an eventually-consistent search index (`github.rs:268`).
  - A single per-PR 403/404 fails the whole poll forever (`github.rs:391, 424`).
- **Jira bump detection compares against one global cursor**, so changes indexed late are absorbed silently (`jira.rs:268-300`).
- **GCal series handling is incomplete** (`sync/mod.rs:287-370`).
  - Series edits and cancellations bump every instance: about 13 Incoming rows for one series.
  - "This and following" edits get a new `recurringEventId`, so the series loses its topic.
  - Events moved past `days_ahead` stay as ghosts on the strip (`gcal.rs:232`).
- **Slack gaps.**
  - Replies to parents older than 24 h in followed channels and DMs aren't discovered on catch-up (`poll.rs:628-657`).
  - Pagination caps silently truncate: history 2000, replies 1000, search 100 (`poll.rs:62-63, 864`).
  - After a settings restart or disable→enable, catch-up is skipped (`socket.rs:123-166`).
  - Flags are acknowledged before the batch commits (`poll.rs:389`).
  - The run boundary is decided from a pre-poll snapshot (`slack.rs:23-49`).
  - Edits after triage are never captured.
- **Gmail:** a non-429 error on one `threads.get` stalls every poll (`gmail.rs:93-98`). Nothing is lost, but sync stops.
- **Obsidian.**
  - Topic note paths collide ("CI/CD" vs "CI-CD"; case-insensitive APFS) and both topics share one file.
  - Note renames aren't tracked.
  - A read error still advances the file's mtime in the cursor, so it is skipped until the next edit (`obsidian.rs:55-58`).
  - Saves silently bypass the Obsidian app when no enabled source matches the vault (`obsidian/save.rs:35-71`).
- **Proton ICS:** an unparseable RRULE silently becomes a single event (`protoncal.rs:446`).
- **`item_messages` ids are rowids reused after delete+insert**, so a split or AI split across a sync can move the wrong message (`sync/mod.rs:315-326`).

**Triage and queries**
- **Confirm, Move, Dismiss and Trash aren't transactional** (`incoming.rs:546-756`).
  - Confirming on a `read_only` Slack source commits the link and `seen`, then errors in `outbox::enqueue`. The held todo is lost.
  - A Jira-held todo with no enabled Jira source fails after everything else is written.
  - Retrying queues the outbox ops twice.
- **Signals linked to an archived topic vanish.** They're in neither the topic list nor Unsorted, but still count in the badge (`incoming.rs:477 vs 501`, `ai/suggest.rs:435`).
- **Jira todo stubs are inserted once per enabled Jira source**, seed and stale ones included (`todos.rs:325-345`).
- **Hand-renaming a source re-ingests the whole lookback** as duplicate unsorted items. Sources removed while the app was closed stay `enabled=1` (`live.rs:215-245`).
- **Two writers race on settings.json.** `categories::save` writes it outside `live::WRITE`, and both use the same `.tmp` name, so a half-written file can be renamed in (→ P0 #15) (`categories.rs:61-73`).
- **`fake_now` is honoured in release builds**, and dev and release share the data dir (`clock.rs:11-17`).
- **Server-side range checks are missing**, so huge `poll_secs` or `quiet_days` panic, and sync threads have no `catch_unwind` (`settings/mod.rs:377`, `sync/mod.rs:557`).
- **`open_url` passes any scheme to `open`/`xdg-open`.** Note links, agent facts and connector URLs reach it (`api.rs:79-83`).

**AI**
- **Suggestions run unserialized and repeat forever.**
  - Every source's poll thread triggers them, personal sources included.
  - Declined items are re-asked forever: about 720 small-model calls/h with 6 sources and 10 declined items.
  - Overlapping runs overwrite `ai_suggest_run` status (`sync/mod.rs:529-622`, `ai/suggest.rs:130-143`).
- **Every active topic goes into every prompt** (`suggest.rs:145-157, 257-271`). At 1,000 topics that's about 50k tokens per item, and small-model accuracy drops as the list grows.
- **AI-proposed topics are created before you confirm.**
  - They're never cleaned up, and names aren't length-capped or sanitized.
  - Prompt injection in a Slack or Gmail message can therefore plant a permanent topic, which then rides in every later prompt (`suggest.rs:298-302, 553-567`).
  - `find_by_name` ignores archived topics, so archived names get duplicated.
- **Suggestions and splits land on items dismissed mid-call**, because there's no `seen = 0` guard (`suggest.rs:435-479`).
- **Merge isn't atomic with the note append**, and a deleted candidate topic aborts the whole suggestion run (`topics.rs:178-186`).
- **"Which topics…" answers silently see only the first ~100 topics alphabetically** (`ai/context.rs:192-232`).
- **Glean owner names aren't checked against the cited evidence** (`glean/ask.rs:368-390`).
- **Embeddings.**
  - The text hash uses `DefaultHasher`, which isn't stable across Rust versions.
  - The model URL is unpinned (`resolve/main`, no sha256).
  - Truncated downloads are accepted and a corrupt file is never re-fetched (`embed/mod.rs:85`, `embed/model.rs`).
  - Vectors aren't deleted on merge or prune, and reused ids pick up stale vectors.

**Agents**
- **Rows pushed to a transcript that isn't loaded get renumbered** (`store.rs:376`, `acp.rs:1815`). The turn then updates the session's *first* prompt row; the new row stays "pending". Incoming's "reply to turn end" hits this.
- **A new approval after a resume can be hidden.** Its Incoming key `req:{session}:{rpc id}` is reused because adapters restart ids at 0, so an earlier dismissal hides it (`incoming.rs:94`).
- **Queued messages stay stuck when the agent exits**, then go out *after* your next message (`acp.rs:671-712`).
- **The agent host can block or double-send** (`agentd/src/server.rs:185-198`, `daemon.rs:248`).
  - A stuck agent's stdin blocks `write`, and `kill` waits on the same lock.
  - The app's 15 s timeout re-sends non-idempotent requests (a double prompt or approval).
  - One stuck agent stalls every other agent through the shared control connection.
- **One invalid-UTF-8 line ends an agent's output stream** (`server.rs:157`).
- **Exit is recorded after `alive=false`**, so a fast respawn reuses sequence numbers. A stale Exit can also hit the new connection.
- **Socket squatting on Linux.** The fallback socket path is predictable in `/tmp` and there's no peer-uid check.
- **`outside`/`rel` paths are compared as string prefixes**, so `/proj-secrets` counts as inside `/proj` (`acp.rs:956`).

**Frontend**
- **Agents thread poll:** a stale delta replaces the whole thread after A→B→A navigation, and history stays missing (`views/agents/state.svelte.ts:63-116`).
- **The topic picker acts on whatever is selected when you pick**, not the item it was opened for. A background refresh in between moves the wrong signal. SearchPalette selects by index, so ⌘T can hit a re-ranked row (`Incoming.svelte:452-468`, `SearchPalette.svelte:33-104`).
- **Split review unmounting on refresh leaves `reviewing` set**, and every Incoming key is dead until you switch tabs (`Incoming.svelte:499, 583`).
- **Data-loading effects take no sequence token**, so out-of-order responses win. Affected: DayStrip, AssistantPane chips (can misstate what context will be sent), Incoming list, Priorities, Topics, SyncStatus.
- **`Set` mutated in place inside `$state`** (`ag.later`), so "Later" doesn't update (`AskCard.svelte:111`, `Tree.svelte:40`).
- **Double-submit:** a second `c` before the reload re-runs confirm and queues a duplicate outbox op. Settings toggles send a stale `!value`.
- **`isTyping` ignores `<select>`.**

## Scale (measured at 200k items unless noted)

| Hot path | Cost | Cause |
|---|---|---|
| Notes `Index::load` on every page load, autosave, and options keystroke | ~2.1 s of SQL, 39 MB of text, plus a disk read of every topic note, **under the global lock and inside the save transaction** | full rebuild per call; no `topic_links(topic_id)` index |
| `topics.list` (every `t` picker open, Topics, TodoForm) | 8.4 s; 1.5 s even with the index | 5 correlated subqueries per topic |
| Embedding `index_pass` every 30 s | 0.64 s per pass under the lock; backfill is O(N²/16): hours of repeated holds | rescans and rehashes the whole corpus to find 16 stale rows |
| `incoming.list` after every action, sync, settings change and 2 s agent tick | unbounded; ~7 queries per signal; `people::suggestions` ~500 ms | no LIMIT, N+1, no partial index on `seen`, global `ui.rev` fan-out of ~10 calls per refresh |
| Series helpers (`confirm_series` runs on every confirm) | ~49 ms per call at 40k items per source | joins on `json_extract(raw_json,'$.recurringEventId')` |
| `items_au` FTS trigger | ~14× the cost of a plain `seen` update | fires on every UPDATE, not just title/body |
| ⌘K prefix search | 200–280 ms per keystroke | no FTS `prefix=` option |
| Slack read-check (every 2 min) | grows with how long a stream stays untriaged | re-reads each open stream from its first message; whole-thread re-reads |
| Agent logs | unbounded; full-file replay under the log lock stalls the agent | no rotation, no offset index |

The scratch DB and bench script are in the session scratchpad (`scratch.db`, `bench.py`).

**Missing indexes:**
- `topic_links(topic_id, state)`
- `items(seen) WHERE seen = 0`
- `events(item_id)`
- `events(start)`, used as a range rather than `substr(start,1,10) = ?`
- `outbox(item_id)`
- `item_messages(at)`
- a series key column

Also: no `PRAGMA optimize`/`ANALYZE`, and no `busy_timeout`.

## Architecture: what to change

1. **DB access.**
   - Use one writer connection plus a small read-only pool (WAL is already on), with a `busy_timeout`.
   - Set a lock-hold budget and keep file and network I/O out of it; notes.rs currently reads every topic note from disk under the lock.
   - Write down one lock order (db → gate → turn → store) and enforce it in a helper.
2. **One worker per source** owns its cursor. Socket nudges and "Sync now" become messages to that worker.
   - Per-stream state goes in rows, not one JSON blob, so partial progress commits and one bad stream is skipped and recorded.
   - Use overlap windows with idempotent dedupe in place of high-water marks on eventually-consistent inputs.
3. **Per-item remote version** (Jira `updated`/changelog id, GitHub `updated_at` + last comment id, gcal etag) stored on `items`. Decide "bump" in `apply`, not in the connector. Add a periodic reconcile of known open items.
4. **Append/upsert messages** with `UNIQUE(item_id, ext_key)`; never delete-and-reinsert. Apply caps only in the UI and AI context. The UI addresses messages by `ext_key`.
5. **Triage actions.**
   - One `in_tx` helper.
   - The UI sends the revision or last message key it rendered, and the backend triages only up to that point (compare-and-set).
   - The outbox `seen` writes become conditional.
6. **Outbox.** Atomic claim (`UPDATE … WHERE state='pending' RETURNING`), a lease with startup recovery of `sent` rows, per-item ordering, and idempotency keys. Do this before Slack reply, Jira transitions and task ticking ship.
7. **Incremental derived state.**
   - Topic aggregates maintained on write.
   - A cached notes index, invalidated on link, topic and note changes.
   - An embedding dirty queue.
   - A cached people resolver.
   - `raw_json` fields used in WHERE/JOIN clauses promoted to real columns.
8. **Time:** store UTC and convert at the edges. Some defaults use SQLite `'now'` (UTC), others local time; DST fall-back and travel will misorder rows.
9. **An AI coordinator.**
   - Single-flight runs and per-item asked-state with backoff.
   - A shortlist of K candidate topics (FTS or embeddings) under a token budget.
   - Proposed topics stay pending until you confirm.
   - A single `delete_topic` helper, or `ON DELETE` rules.
10. **Agents.** `on_event` becomes a pure state transition that returns follow-up actions, run after the gate is released. Add a per-spawn generation to conn, request and seq keys. Classify shell commands as unknown unless known to be read-only.
11. **Settings.**
    - A single writer (lock, unique temp file, fsync).
    - Stable source ids in `settings.json` with a reconcile pass at startup.
    - Tolerant startup: last-good values plus an error banner.
    - Demo data in a separate DB, never written to the configured vault.
    - Secrets written atomically and failing loudly on parse errors.
12. **Frontend.**
    - Per-domain revisions pushed from the core (Tauri events) in place of the global `ui.rev` and 2–3 s polls.
    - A paged, delta-based Incoming.
    - Shared `latest()` / `mutation()` helpers (sequence token, pending set, rollback).
    - Keyboard layers (modal / view / global).
    - Selection keyed by id, with the action's target captured when the action starts.
    - Split `Incoming.svelte` and `Settings.svelte`.
    - Generated TS types (ts-rs or specta).
13. **Tests.** All current tests are single-threaded fixture tests; none of the races above are covered. Add concurrent-sync and triage-during-sync tests alongside each fix.

## Suggested order

1. **Quick, contained, high-value fixes:**
   - The agents deadlock (P0 1–2).
   - Settings key fall-through (11).
   - Devserver CORS/token (10).
   - Atomic secrets (9).
   - The `search_feedback` merge (13).
   - `on_confirmed` seen (7).
   - Seed guard (14).
   - Tolerant settings startup (15).
   - The `items_au` trigger and missing indexes.
2. **Sync worker per source + message upsert + per-stream error isolation** (P0 3–6). This is the Slack "never miss a message" core.
3. **Triage compare-and-set + transactions + outbox claim/recovery** (P0 8, 16; P1 triage).
4. **DB read pool + incremental derived state** (the scale table).
5. **shell.rs inversion** (P0 12) and the remaining agents items.
6. **The AI coordinator, then frontend async/keyboard infrastructure.**
